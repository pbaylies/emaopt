# emaopt — EMA-accelerated statistical optimization

A research library for one question:

> **What information from the past is this algorithm currently throwing away —
> and does keeping it change the quality you get per unit compute?**

**Primary outcome:** objective achieved per example processed and per unit
wall-clock compute, at matched initialization and target quality. Every comparison
here is stated that way, and the library is deliberately neutral about the answer:
an EMA, a cumulative average, a Robbins–Monro schedule, an adaptive state — or
nothing at all.

`emaopt` separates every estimator into four stages:

```text
measure(batch) -> update_state(...) -> decode(state) -> objective(data)
```

and makes the **state-update law replaceable**, so the same algorithm can run as a
conventional one-pass rebuild (`Replace`), a cumulative average, an EMA, a
bias-corrected EMA, a Robbins–Monro schedule or an effective-sample-count adaptive
EMA — without rewriting the estimator. The reference case is **e-means**, the EMA
k-means algorithm from Meta FAIR (arXiv:2611.09501), reproduced here as P0.

Status: **0.1.0 beta**, MIT licensed. Measurements that this repository can
regenerate are paired with the script that does it under [`scripts/`](scripts/)
and with the record it writes under [`evidence/`](evidence/).

## Install

```bash
pip install emaopt              # numpy only; no torch, no sklearn
pip install "emaopt[gpu]"       # optional torch device arms
pip install "emaopt[reference]" # optional sklearn, for the parity tests
```

The default path is NumPy + float64 and imports nothing else. Verify a checkout
with `python -m pytest tests/`.

The compiled host E-step is optional and never built automatically — the artifact
is per-machine, so the C source ships and you build it once. **The only
requirement is a C compiler** (`cc`, plus OpenMP):

```bash
python -m emaopt.kernels.build                  # --backend c is the default
python -m emaopt.kernels.build --check          # verify an existing artifact
# read-only site-packages: build elsewhere and point the loader at it
python -m emaopt.kernels.build --target ~/.cache/emaopt/libegmm_diag.so
export EMAOPT_HOST_KERNEL_PATH=~/.cache/emaopt/libegmm_diag.so
```

`--backend cuda` builds the torch-free device E-step instead (`nvcc` required,
opt-in at runtime with `EMAOPT_DEVICE_ESTEP=1`).

A numba backend covers the row log-density, fused E-step and e-means epoch
runner with a JIT. It is opt-in twice -- `pip install "emaopt[numba]"` and
`EMAOPT_NUMBA=1` -- because the first call in a process pays a JIT compile. The
narrow path is a compiled row loop; the wide path uses two BLAS GEMMs plus a
compiled softmax, because the scalar wide form loses to NumPy's GEMMs. The
recorded table forces the row kernels on every shape; normal dispatch keeps the
measured work/width gates.

```bash
pip install "emaopt[numba]"
EMAOPT_NUMBA=1 python -c "import numpy as np; from emaopt import GaussianMixture; \
GaussianMixture(8, covariance='diag').fit(np.random.default_rng(0).normal(size=(20000, 64)))"
```

The arms' parity and measured crossover are regenerated by
[`scripts/gen_hostkernels.py`](scripts/gen_hostkernels.py) into
[`evidence/host_kernels.json`](evidence/host_kernels.json).

Without a build every call falls back to NumPy; `emaopt.hostkernels.status()`
reports which path is live. `EMAOPT_HOST_KERNEL=numpy` disables it explicitly.

## Quick start

```python
import numpy as np
from emaopt import emeans

x = np.random.default_rng(0).normal(size=(20_000, 32))
res = emeans(x, k=64, nepochs=5)      # batch size + step from the e-means laws
res.centroids, res.labels, res.objective
```

Swap the update law — same algorithm, different memory of the past:

```python
from emaopt import EMeans, LloydKMeans, GaussianMixture
from emaopt.state import EMA, AdaptiveEMA, Replace

lloyd    = LloydKMeans(k=64, niter=25)                     # Replace, full batch
stream   = EMeans(k=64, nepochs=5)                          # EMA + cosine + revival
gmm_b    = GaussianMixture(8, covariance="diag", updater=Replace())
gmm_ema  = GaussianMixture(8, covariance="diag", updater=EMA(alpha=0.05))
adaptive = GaussianMixture(8, covariance="tied", updater=AdaptiveEMA())
```

### Three entry points, and which to use

| entry point | batch decision | use it for |
|---|---|---|
| `emeans(x, k, nepochs=...)` | the e-means laws, `max_points_per_centroid` subsample | the reference recipe, drop-in |
| `SMeans(k).fit(x)` | the e-means laws | the s-means recipe (D^1.5 seeding, anisotropic revival, shrinkage); opt-in |
| `Model(...).fit(x)` | the model's own default | everyday fits |
| `fit(Model(), x, FitConfig(...))` | `FitConfig.batch_size` | sweeps and recorded experiments |

`FitConfig.batch_size` accepts `"auto"` (default — the optimizer's own law),
`"full"`/`None` (one batch per pass) or an explicit `int`. The default is `"auto"`
precisely so the runner cannot silently override a model's fitted batch law; every
recorded fit in the ledger passes an explicit size, so no published number moved.

### Streaming

Blocks in, sufficient statistics out, `O(kd)` state:

```python
import numpy as np
from emaopt import CentroidStat, GaussianMixture, MemoryBudget, partitioned_stat, stat_fit

x = np.random.default_rng(0).normal(size=(20_000, 32))
stat = CentroidStat(16, mode="ema", alpha=0.1)
result = stat_fit(stat, x, block_size=512)             # one pass, 24 MB @ 100k x 512
merged = partitioned_stat(lambda: CentroidStat(16, mode="sum"), x, block_size=512)
plan = MemoryBudget.probe()                             # MemAvailable / cgroup headroom

# any optimizer through the same protocol
model = GaussianMixture(8, covariance="diag")
streamed = stat_fit(model.as_stat(), x, block_size=8192, prepare=x[:8192])
```

`FitConfig(budget="auto")` measures available memory at call time and resolves
batch-vs-stream itself, recording the decision in
`FitResult.extras["compute_plan"]`.

### Probability calibration

Calibration is opt-in. `auto_calibrate` chooses temperature scaling when held-out
labels exist, prior correction when only a target marginal exists, and raises when
neither does — it never calibrates against the model's own argmax.

```python
from emaopt.calibration import auto_calibrate, calibration_report

probs_cal  = model.predict_proba(x_cal, params)      # params from Model.fit
probs_test = model.predict_proba(x_test, params)
cal = auto_calibrate(probs_cal, y_cal)               # labels -> temperature scaling
report = calibration_report(probs_test, cal.transform(probs_test), y_test)
```

`calibration_report` reports NLL, Brier, top-label and classwise ECE, MCE,
AUROC/average precision, an explicit base-rate control, and equal-mass reliability
bins. **Honest reading** (REPORT §9): calibration fixes the marginal
(ECE 0.111 → 0.007), but on the LAION pair task the posteriors' AUROC is 0.563 —
below a constant base-rate predictor on Brier/NLL. The instrument works; the
signal it was asked to carry does not exist at that width. At d=64 the same
detector reads 0.737.

## Support tiers

Status is an evidence claim, not a maturity boast. **Mature** means a reference
library matches on the same data, **control** means it exists to bound a variant,
**research** means it works and is tested but has no acceptance path of its own.

| tier | modules | what you get |
|---|---|---|
| mature | `algorithms/{kmeans,emeans,gmm}`, `state/`, `stream.py`, `plan.py`, `budget.py`, `threads.py`, `calibration.py` | replicated against sklearn / FAISS, pinned by the suite |
| control | `algorithms/{pca,lda}`, `benchmarks/`, `analysis/` | baselines the claims are denominated in |
| optional | `levels.py`, `hostkernels.py`, `gpu.py`, `gpu_pca_ica.py`, `gpu_emeans.py`, `basemap.py`, `algorithms/umap.py`, `pipeline.py` | measured opt-ins on the mature paths; defaults untouched |
| research | `sparse_decomp`, `vq`, `pq`, `scalar_quant`, `nmf`, `dictionary`, `ica`, `matrix_factorization`, `spectral`, `subspace`, `robust_pca` | working, tested, no reference parity claim — see the module docstrings |

Performance opt-ins are the same tradeoff under a name rather than a bag of flags:

```python
from emaopt import GaussianMixture, levels

with levels.use("auto"):                     # compiled E-step, f32 reductions
    result = GaussianMixture(16, covariance="diag").fit(x)
```

`quality` is the NumPy/float64 reference (drift budget 1e-12 nats), `auto` moves
only the reductions (measured 2.9e-07 nats of drift; the speedup is
process-dependent), `performance` additionally moves the E-step — a
**device-arm** setting; on host fits it is bit-identical to `auto`.

## Basemap pipeline (UMAP + GPU e-means + placement + Voronoi)

A scalable hierarchical layout for large image/embedding datasets (the MONET-style
scheme): embed a sample, train centroids at increasing scales, embed the top
level, place mid/fine centroids and then all rows next to their parents, then
cut the finest level into Voronoi clusters and push the clusters apart.

The whole structure can be wired in one call:

```python
import numpy as np
from emaopt import run_basemap

result = run_basemap(
    features,                 # (n, d) embeddings
    top_k=32_000,             # top-level centroids (UMAP'd)
    mid_k=260_000,            # mid-level centroids (placed around top)
    fine_k=1_000_000,         # finest level (placed around mid)
    nepochs=5, groups=2_000, seed=0,
)
# result.top_xy / .mid_xy / .fine_xy / .tail_xy  -> 2-D placements
# result.voronoi (groups cells over the fine centroids) + result.push_apart
```

The pieces are also public and composable:

```python
import numpy as np
from emaopt import (
    umap_embed, UMAPConfig,
    emeans_gpu_fit,
    nearest_parent, place_around_parents,
    voronoi_cut, push_apart,
)

# 1. embed a sample (UMAP-style, fast, device-first) — cheap sanity check of the fit
res = umap_embed(sample, UMAPConfig(n_neighbors=15, n_epochs=200), device="cuda")

# 2. centroids at scale, entirely on the device (32k / 260k / 1m)
fit = emeans_gpu_fit(x, k=32_000, nepochs=5, seed=0)

# 3. UMAP the top-level centroids (cheap: 32k rows), place the tail
#    next to their parents
top = umap_embed(fit.centroids, UMAPConfig(n_neighbors=15, n_epochs=200), device="cuda")
parent_xy = top.embedding
pids = nearest_parent(x, fit.centroids, device="cuda")
tail_xy = place_around_parents(pids, parent_xy, spread=0.3, seed=0)
#    offsets scale to each parent's own local 2-D neighbour spacing;
#    pass local_spacing=False for the global-median fallback.

# 4. cut the top level into Voronoi cells and push them apart
vr = voronoi_cut(parent_xy, groups=2_000, iterations=60)
pa = push_apart(vr.centers, min_separation=0.1)
```

Stages 2-4 are device-first (torch, chunked, never an (n, k) distance matrix);
the default host path stays NumPy float64 and unchanged. Stage 1 is a fast
UMAP-*style* embedding: fuzzy membership + SGD layout with Monte-Carlo
negation — not bit-identical to UMAP. `emeans_gpu_fit` keeps the host's exact
law (fitted batch size + cosine alpha grid, EMA fold) and was measured at
30k rows x 128 dims x k=1000 on a 4090: 0.25 s device vs 4.2 s host (~17x),
overlap -0.07% objective gap; the same fit at 100k x 128 x k=5000: 3.1 s vs
85.1 s (27.4x), objective gap -0.27%, 0 dead clusters. UMAP at 50k x 128
(100 epochs): 3.0 s, adjusted rand 1.0. Honest limits: no cluster revival on
the device arm (host RNG walk — the config raises if `revival=True`), no
6M/100M-row run yet (2-4x validated at real scale and at synthetic 1m scale,
both bounded in GPU memory). The Voronoi stage is a straightforward Lloyd pass
with a deterministic greedy k-means++ init over a subsample — Lloyd converges
and every group is used at ≤1k groups (chunked row processing keeps it inside
GPU memory at 1M rows); at 2k groups Lloyd plateaus (converged=false) — reported
honestly, not masked with a looser tolerance. `run_basemap` wires the full
pipeline (top UMAP → mid → fine → rows → Voronoi → push apart) with per-parent
local spacing for the placement; see the example above and
`scripts/run_basemap_monet.py`.

`scripts/bench_basemap.py` records the timings; the JSON record is
`evidence/basemap_bench.json`. **Performance opt-ins** parity-wise:
`emeans(x, k)` (host) remains the reference; the GPU arm is an opt-in.

### Host kernels

Milliseconds, measured on this machine (24 cores, 8 threads; each arm does
about a second of timed work after a warm-up, in batched bursts reported as the
median burst mean, and the generator waits for a quiet host before timing -- the
budget, call count, load average and the wait are in the record), float64.
The four arms are `numpy` (the reference path), `C` (the packaged
`kernels/egmm_diag.c`), `numba` (the opt-in JIT backend) and `internal` The
numba column forces its row kernels on every shape for the record; normal
dispatch sends only wide rows (`d > 128`) to numba when it is enabled, and keeps
the measured work gate for small batches.

Log-density, `log N(x | mu_j, diag cov_j)`:

| shape (n × d, k) | numpy | C | numba | internal |
|---|---|---|---|---|
| 8192 × 64, k=16 | 0.73 | 0.31 | 0.82 | 0.32 |
| 4096 × 512, k=16 | 2.19 | 1.37 | 2.03 | 1.33 |
| 3000 × 8, k=8 | 0.09 | 0.03 | 0.05 | 0.02 |
| 8192 × 320, k=64 | 6.64 | 5.35 | 5.86 | 5.38 |

Row log-sum-exp, the scoring pass:

| shape (n × d, k) | numpy | C | numba | internal |
|---|---|---|---|---|
| 8192 × 64, k=16 | 0.91 | 0.14 | 0.16 | 0.15 |
| 4096 × 512, k=16 | 0.47 | 0.08 | 0.09 | 0.08 |
| 3000 × 8, k=8 | 0.23 | 0.04 | 0.04 | 0.03 |
| 8192 × 320, k=64 | 2.28 | 0.45 | 0.53 | 0.46 |

The fused E-step (logits + softmax + statistics + NLL). The numba row pass is
compiled; its statistic reductions use BLAS over the responsibility matrix.
On wide rows the log-density part is also BLAS-backed (see below). The `internal`
and `numba` columns are measured alternatives, not the dispatched arm; C remains
the shipped path.

| shape (n × d, k) | numpy | C | numba | internal |
|---|---|---|---|---|
| 8192 × 64, k=16 | 2.71 | 1.09 | 2.10 | 0.91 |
| 4096 × 512, k=16 | 4.37 | 4.13 | 4.32 | 2.99 |
| 3000 × 8, k=8 | 0.49 | 0.13 | 0.16 | 0.14 |
| 8192 × 320, k=64 | 17.42 | 13.38 | 13.77 | 11.96 |

e-means, end to end (includes seeding, decoding and the scoring pass; the epoch
kernel is one term in it; `(loop)` marks a runner that declined this shape and
left the fit on the NumPy loop):

| fit | numpy loop | numba runner | internal runner | numba speedup | internal speedup | numba Δ | internal Δ |
|---|---|---|---|---|---|---|---|
| 3000 × 8, k=8, 5 epochs | 27.99 ms | 2.47 ms | 2.34 ms | 11.3x | 12.0x | 0.0e+00 | 0.0e+00 |
| 8192 × 320, k=64, 5 epochs (diagnostic) | 140.07 ms | 140.19 ms (loop) | 140.15 ms (loop) | — | — | 0.0e+00 | 0.0e+00 |

Reading it: the two compiled row kernels are within a hair of each other
wherever they meet -- internal 0.32 against C 0.31 at `8192 × 64`, internal 1.33
against C 1.37 at `4096 × 512`, internal 0.02 against C 0.03 at `3000 × 8` --
and at `8192 × 320` internal is 5.38, C 5.35, numba 5.86 and numpy 6.64. Row
log-sum-exp is the compiled arms' pass: 0.14-0.16 at `8192 × 64`, 0.08-0.09 at
`4096 × 512`, 0.03-0.04 at `3000 × 8` and 0.45-0.53 at `8192 × 320`, against
NumPy's 0.91, 0.47, 0.23 and 2.28. The fused E-step goes to internal at three
shapes: 0.91 against C 1.09 and numba 2.10 at `8192 × 64`, 2.99 against C 4.13
and numba 4.32 at `4096 × 512`, and 11.96 against C 13.38, numba 13.77 and numpy
17.42 at `8192 × 320`; C keeps `3000 × 8` by a hair (0.13 against 0.14). On a
quiet host, four fresh processes spread 1.02-1.09x for every arm, while the run
before this one had the session's own processes on two cores and moved every arm
20-45% (C's wide log-density 5.59 there against 5.35 here; NumPy's wide step
17.11 against 17.42); the record carries the 1-minute load average, so read
cells within a table and expect the wide orderings to move -- C's wide step has
measured 9.99, 13.38 and 17.11 ms across runs. At `3000 × 8` both compiled epoch
runners collapse the interpreter-bound updates: numba is 2.47 ms (11.3x) and
internal 2.34 ms (12.0x), same objective to `0.0e+00`. At `8192 × 320` the
runners now decline (per-update work 10.5M, past the 4.5M gate) and the fit
keeps its NumPy loop: 140.07 ms against the 167-198 ms they took while still
being selected.

Why the shipped C log-density uses direct differences: the tiled row was
the model, because it carries one accumulator per component instead of two and
reads `meanT` rather than the larger `miT`/`quad_bias` pair. C exposes the same
`c`-outer/`j`-inner row (output row as scratch). A two-round A/B in one process
(20 reps per round, same prepared buffers) put direct at 0.7-0.8x the expanded
form at `8192 × 320` (2.93-3.40 ms against 4.11-4.19) and within noise at the
narrow shapes (0.34-0.44 against 0.36-0.76 at `8192 × 64`; 0.79-1.21 against
0.83-0.91 at `4096 × 512`) -- those timings include the per-call preparation,
which is why the narrow shapes do not separate. The old expanded entry point
remains for ABI fallback only.

Why the wide Numba log-density uses BLAS: NumPy is not faster because its
softmax is better. It rewrites the diagonal quadratic as two GEMMs,
`x @ (mean/cov).T` and `(x*x) @ (1/cov).T`, and OpenBLAS does blocked,
threaded work over `d`. The original scalar Numba kernel reduced over `d` once
per `(row, component)`; at `8192 × 320, k=64` its log-density measured 15.5 ms
against 5.7 ms for the two-GEMM form. The shipped wide path now uses the same
two products and keeps only the softmax/normalisation in compiled row code. The
assembled step is 13.77 ms at that shape in the current record, above C's
13.38 and internal's 11.96 (the ordering moves between runs: C's wide step has
measured 9.99-17.11 ms there).

The tables are stored verbatim in
[`evidence/host_kernels.json`](evidence/host_kernels.json) under `markdown`, and
`tests/test_evidence_record.py` fails if this section drifts from it. The ratios
move between runs on a shared machine; the record is what they are read from.

### Recorded, not regenerated here

Kept because the comparisons are the point, and labelled so they are not
mistaken for gates. No script in this repository reproduces these:

- GMM (diag) at 100k x 512, k=8: same held-out NLL as sklearn (191.103 both),
  2.68 s against 10.82 s; streaming that fit 0.54 s at a 24 MB peak, against
  2.68 s and 783 MB batched.
- e-means wall time against sklearn / FAISS: 0.56x / 0.06x at 3k x 8, 0.13x /
  0.60x at 20k x 32.
- s-means (opt-in), corrected, warm, two seeds: 7.632 vs 7.632 MSE at 3000 x 8
  k=8; 31.900 vs 32.341 at 20000 x 32 k=16 (23.5 vs 32.2 ms); 35.372 vs 31.563
  at k=64 (82.4 vs 121.9 ms); 9.473 vs 9.327 at 20000 x 8 k=128. FAISS e-means
  stays faster at k=64 (34.45 ms).
- coreset initialisation: median 1.041x -> 1.017x MSE against full-data
  k-means++, and a coreset four times larger beat k-means++ at 20k x 32 k=64
  (34.96 vs 37.06 MSE in 95 vs 156 ms).


Which arm runs is a function of total work and width, and the crossover is
measured rather than asserted: the C artifact serves the direct-difference
log-density and the fused step, the numba backend takes wide log-density and
fused-step calls when it is enabled, and NumPy is the floor everywhere else.
[`evidence/host_kernels.json`](evidence/host_kernels.json) is that measurement.



The opt-in **s-means** arm (`algorithms/smeans.py`) adds the four mechanisms of
[s-means](https://github.com/suayptalha/s-means) to this engine: subsampled
greedy D^1.5 seeding, distortion-weighted anisotropic revival, empirical-Bayes
shrinkage of the final centroid, and a power-cosine step. The module docstring
records what each mechanism was measured to buy and where it loses; the
initialisation is the lever, and the sweep that showed it is not part of this
tree.

## Where the rest lives

- [`scripts/gen_hostkernels.py`](scripts/gen_hostkernels.py) — rebuild the C
  artifact and regenerate the kernel parity and timing record.
- [`evidence/`](evidence/) — the machine-readable records those scripts write.
- Module docstrings — the per-algorithm notes: what was measured, on what shape,
  and what the code deliberately does not claim.

A result is only a result when it is a record: algorithm, variant, dataset shape,
batch size, seed, initialization, state update, hardware, objective, compute, and
status (`hypothesis` / `replicated` / `rejected` / `inconclusive` / `baseline`).
Failed experiments stay in the ledger.

## latent-scope integration

emaopt can serve as the GPU backend for Ian Johnson's
[latent-scope](https://github.com/enjalot/latent-scope) (embed → project →
cluster → explore). An optional bridge lives in `emaopt.integrations`:

```python
import emaopt.integrations as integ

integ.install_latentscope()   # idempotent; patches latent-scope's GPU paths
```

or, without patching:

```python
emb, backend = integ.run_umap(embeddings, neighbors=15, min_dist=0.075, seed=0)
labels, centroids = integ.run_emeans(embeddings, n_clusters=32, nepochs=5)
```

emaopt's GPU e-means is the same algorithm latent-scope's basemap scheme is
built on. Details and the exact upstream patch (3 files) are in
`docs/latent-scope-integration.md`. It is guarded: without latent-scope
installed it is inert, and without CUDA it falls back to CPU. Tested against a
fresh clone of latent-scope (`_reduce_umap` → 0.7 s 2-D emaopt embedding,
`_run_kmeans` → ARI 1.0 on synthetic blobs).
